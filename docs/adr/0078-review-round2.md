## high

### **[high] H1 — 撤权承诺只覆盖后续分派，未定义在途工作及派生执行权限的失效边界**

- **位置**：ADR:149–152、259–278、291–304、341–348；计划:532–538、640。
- **事实**：正文明确“later dispatches are refused”，共享 guard 覆盖五个执行入口，旧 Chief 会话不能降级绕过；计划要求缩范围、过期、撤销后“立即拒绝”。但未定义已提交、尚未启动的执行者、运行中的执行者及其子会话是否继续，是否继承 Chief 委派的实时限制，或只在最初 admission 检查一次。现有 `delegateAndStartAgentSession` 创建独立 executor Delegation，INSERT 未记录 `parent_delegation_id`（`apps/api/src/agent/commands.ts:1180–1197`）；现有 revoke 按所撤 delegation 定位 token/session（同文件:578–630）。Schema 虽有 parent 字段（`packages/db/migrations/v1/0001_v1_baseline.sql:323`），不能据此推定当前 forced assignment 已有撤权传播。
- **影响**：仅在事务内“读到 live”不等于与并发修订建立顺序，也不等于能撤销另一份已派生权限。可出现“总管已不能再派工，但它刚创建的 executor 仍按旧范围继续”的实现，而 UI 仍宣称这次委派已撤销全部效果。已排队的启动、重试或外部动作尤其容易落在边界之外。具体运行时绕过**待验证**；缺失失效契约是确定事实。
- **建议**：在本节增加一张状态表，并由 F2/F3 同步验收，推荐采用以下规则：
  1. 修订/撤销与新分派锁定同一授权版本，定义提交顺序；先提交的撤权必须使随后提交的分派拒绝。到期在最终授权检查点按当前时间判定。
  2. 已提交但未启动的派生工作，在最终 admission 再查当前 appointment、委派及目标工作项版本；不再满足者取消启动，不消费新的预算。
  3. 持久保存派生 executor/child/重试与来源 Chief 委派、任命代次的关系；失效后至少拒绝不再被覆盖的普通写入和受平台管理的外部动作。明确是否停止全部派生会话，还是仅停止受本次缩范围影响的会话。若产品有意允许已分派工作独立继续，必须明确这是独立存续授权，UI 不得称其已被撤销，并给出单独停止入口。
  4. 明确缩范围后旧 revision 必须重新读取；仍落在新范围内的工作可自主重新提交，无需人类逐项批准。修改 Work Item 的描述不应被自动解释为扩大委派，也不应悄悄让在途旧目标继续执行。
  5. 对已进入外部进程/已完成的不可逆动作，只承诺阻止后续平台动作、发送取消请求并记录结果，不承诺追溯撤回。ADR:110–116 已正确说明 WorkMesh Stop 不会直接杀掉 harness 命令，应保留这一限制。

  必测：dispatch 与缩范围/撤销交错提交、入队后撤权再启动、运行中及子会话撤权、到期边界、重试/worker 恢复、同 key 重放不产生第二次效果。既有日志与结果事实保留。

### **[high] H2 — “与 0062 同构”不成立，缺少合取规则及两个执行关口的精确定义**

- **位置**：ADR:16–17、54–56、266–283、295、306–314、442；计划:528–529、642、672、706–709；ADR 0062:13–25。
- **事实**：0078 把 Chief delegation 与 autonomy policy 称为 “the same kind of thing”，并据此断言不冲突。0062 实际规定：policy-authored decision **在普通授权检查通过之后**满足 Approval，不能绕过 delegation/capability/scope/Stop；策略为 workspace 的 `human_required | yolo`，Project 可排除。它不是针对某个 agent/目标的 Delegation。当前 `requestApproval` 在 YOLO 下直接写 `source='workspace_policy'`（`apps/api/src/agent/commands.ts:2935–2960`）。0078 同时说“Request authority it lacks”走 `requestApproval`、“only a Human can grant”，又称“two human gates”保持不变；没有说明两道关口究竟是何种领域命令、是否为 Approval、由谁满足。
- **影响**：实现者可能把“策略已批准”当作可创建/扩展 Chief 委派的凭证，或者反过来把“已有委派”当作跳过动作 Approval 的理由。另一种冲突是把“确认方案/审核改动”无条件实现成人工逐项阻塞，同时又宣称完全不收窄 0062。文档本身尚未允许这些绕过，但不能用“并行”二字决定组合行为。
- **建议**：保留“并行”作为功能关系，删除“因此同构”的推论，在本节写出可直接实现的规则：

  > Chief Delegation 决定谁可以在何种目标、资源、能力及期限内发起分派。Approval Autonomy Policy 仅决定一个仍需 Approval 的具体动作可否由策略作出批准。执行要求有效 Delegation **且**其他身份、能力、scope、Stop、revision、lease 等检查全部通过，**且**在动作需要 Approval 时有满足该动作绑定的有效 Approval。任何一项拒绝均拒绝；二者不构成 OR 或 fallback。

  创建/扩展委派须走有权限 Human 的专用受治理命令，不能把任意 Human Approval 或 policy Approval 直接兑换成授权；`requestApproval` 可以承载请求与通知，但不自行修改 grant。明确 `source` 保留来源，不能仅凭记录中的 Human actor ID 推定本次人类确认。

  再为“确认方案/审核改动”各列：受保护状态迁移、plan version/精确 diff 或 head 绑定、可决定的 actor/source、何种修改使确认失效、服务端执行位置。若它们使用 0062 管辖的 Approval，则按该策略解释，不能无条件称为逐项 **human** gates；若要求即使 YOLO 也必须真人，就明确写成仅针对这两道关口的政策差异，不能继续笼统声称没有差异。此处须写清产品语义，不要求恢复分派审批。

  计划风险表和验收矩阵同步增加：无委派 + YOLO 拒绝、委派越界 + policy approved 拒绝、合法委派 + human_required 的普通自主分派成功、受保护动作仍走对应关口、即时自动批准与 pending reconciliation 均不扩委派、变更 plan/head 后旧确认不能复用。

### **[high] H3 — 总管自己的能力上限与“可授予执行者的能力上限”没有区分**

- **位置**：ADR:157–183、270–278、439、448–453；计划:503–510、519–538。
- **事实**：默认集仍只有六项协调能力，其中含 `agent:delegate`；`repo:write_branch`、`repo:merge`、`deploy:*`、`secrets:use`、`admin:*` 均在需单独批准的组。新委派仅笼统列 capabilities/scope，未说明这些是 Chief 直接执行权限还是下游 dispatch payload 的上限。现有 forced assignment 的调用方检查关注 `agent:delegate`（`apps/api/src/agent/commands.ts:866–871`）；`requestedCapabilities` 的检查是目标 agent definition 与目标 Team grant 的交集（同文件:899–923）。因此复用现有检查，不会自动得到“目标执行者权限受本次 Chief 委派约束”。旧稿的逐次授权曾明确绑定 target agent、capabilities 和预算；新稿删除了这层精确绑定，却没写清由何种常设约束替代。
- **影响**：默认 Chief 不能直接 merge/deploy，不等于不能让一个原本获准执行这些动作的 agent 去做。把二者混称为“默认排除有效”会让用户高估本次目标委派的限制。反过来，简单强制子能力永远是 Chief 直接能力的子集，又会让默认总管无法调度正常代码工作。下游既有能力和 Approval 检查仍然存在，**不能据此宣称已经能无审批 merge/deploy**；本次缺口是目标级授权边界未定义，实际越界执行待验证。
- **建议**：分别定义 Chief 的直接能力与此目标允许分派的执行者角色/能力/资源上限。人类确认目标委派时一次确认后者；每次自主分派把 target、requested capabilities、resource scope、预算、有效期与该上限及目标实时授权取交集，禁止从目标已有的较宽 grant 借出超出本次目标的权限。若产品选择默认允许调度代码执行而 Chief 不能亲自写代码，应把两张默认表明确写出；若部署/秘密/管理仍默认禁止下游执行，也需在分派上限中明确排除。不要靠自由文本目标或模型自行判断“仍属原目标”来扩边界。

  F1/F2 增加反向测试：默认 Chief + 已持 `repo:merge`/deploy/secrets 权限的目标 agent；无该目标分派上限时拒绝，有明确常设授权时允许调度但仍保留目标动作自身的 Approval/Stop 等检查。所有五个入口以及派生 child/retry 均适用。

## medium

### **[medium] M1 — 保留最大使用次数，却删除了原子计数契约及并发验收**

- **位置**：ADR:270–282、341–345；计划:519–522、535–538、639–643；本次 F2 diff。
- **事实**：委派仍有 maximum use count、预算与 exhausted 错误，但执行正文只要求“校验 live”，没有说明何时增加计数、预留预算，以及失败/重放/重试如何计费。旧测试“两次消费只有一次生效”被删除，没有替换为“常设委派余量只剩一次时并发只有一次生效”。ADR 的跨 activation 累计预算确实仍在，但不能替代一次 activation 内多个自主分派的用量定义。
- **影响**：两个不同 key 的并发分派可各自看到剩余一次；只做 live 检查的实现可绕过次数上限。相反，重放重复扣次数又会提前耗尽委派。删除一次性授权消费是合理的，删除用量核算不是其必然结果。
- **建议**：保留可复用委派，增加按逻辑 dispatch 身份记录的使用/预算台账；剩余量校验、预留或扣减、session/event/outbox 在同一事务提交，重放不重扣。明确一次派工跨多入口不能重复计数，新 execution retry 是否算新使用，以及失败预留如何释放；修订委派不能无意清零已用量。F2 加并发最后一次、不同 key、相同 key、失败回滚、重试与跨会话累计用量测试。此处的 usage accounting 不应再叫“一次授权的消费”。

### **[medium] M2 — 迁移与规格出口仍要求旧的可消费授权，且去重不能改用委派 ID**

- **位置**：ADR:370–372、464–466、509–511、541–542、566–574；计划:239、512–538。
- **事实**：ADR Spec changes 仍定义 `Dispatch authorisation (a consumable binding...)`，OpenAPI 仍要新增该 binding 的 consumption errors，Migration 仍要求其 consumption。消费协议还说分派效果由 `authorisation binding` 独立去重；Delivery 仍说新增 `precise action binding`。这些不是放在历史撤回段落中的描述。计划 F2 已改为可复用的总管委派，依赖图却还叫“F2 分派授权绑定”。
- **影响**：按正文实现会得到 standing Delegation；按迁移/接口清单实现会重新引入逐次可消费授权。若直接把旧 binding 替换成 delegation ID 做去重，同一委派下第二次合法派工会被误判重复；若只删去旧 binding，则丢失分派效果去重承诺。
- **建议**：统一改为“Chief delegation / 总管委派”，并独立命名“dispatch record / 分派记录”和 M1 的使用台账。明确 delegation ID + revision 是授权来源，不是 dispatch 的唯一身份；仍用稳定逻辑操作 ID、幂等键及请求内容冲突规则避免重复效果。将 Migration、CONTEXT/OpenAPI 变更清单、Consumption、Delivery、Consequences 和计划依赖图一次同步。如果 `precise action binding` 指现有受保护动作的 Approval，应明确注明它不是每次分派的授权绑定。

## low

### **[low] L1 — 状态行把 F0 的设计前置改成实现依赖，与依赖图形成回环**

- **位置**：计划:4、238–241、490。
- **事实**：状态行写“F0 依赖 F2”，而依赖图由 F0 流向 F1/F2，F0 标题仍写“必须最先做”。原状态行是“F0 阻塞于 F2 的授权收窄待确认”，本次 owner 已解决口径选择，却留下未限定阶段的反向依赖。
- **影响**：任务编排会把 F0/F2 相互阻塞，或把“先冻结授权设计”误当成“先实现依赖团队房间的 F2”。这是计划不一致，不是授权绕过。
- **建议**：将状态行改为“F2 的自主分派方向已定；授权契约需按本轮审查补齐并在 F0 实施前冻结；实现顺序以 F0 → F1/F2 → F3 为准”，或给出另一份明确无环的顺序。设计冻结与实现依赖使用不同措辞。

## 七项重点核对

### 1. 在途与运行中工作的边界

| 情形 | 已写明 | 尚未写明 |
| --- | --- | --- |
| 缩范围、过期、撤销后的新分派 | live 校验；计划说立即拒绝 | 并发提交顺序、到期检查点；缩范围后仍合法工作如何使用新 revision |
| 旧 Chief 会话、换届 | 持久 Chief 上下文，不准降级绕过；不再派工 | 除分派以外可保留哪些读写，旧会话是否停止 |
| 已提交、尚在队列中的分派 | activation 启动前重新准入 | 这是否覆盖每个下游 executor 与 worker/outbox 执行点 |
| 正在运行的 executor/child | 各自仍受一般 Delegation/Stop 约束 | 来源 Chief 的缩范围/撤权是否传递，传播关系与失效规则 |
| 已进入外部 harness 的命令 | 平台 Stop 不直接中止进程 | 取消请求、结果不确定及后续平台写入如何记录和处理 |

模型可以实现；“引用一个可撤销委派”本身不足以保证所有已派生工作都可撤销。见 H1。

### 2. 与 ADR 0062 的关系

可以并存，**不构成同构的两套可替代授权**。Delegation 是针对主体和资源的执行权限；0062 的 Approval Autonomy Policy 是满足受保护动作审批条件的政策。其共性是可事先设置且可调整，不足以证明权限覆盖面相同。差异应写进 0078 的 Relation 段与 Spec changes，并同步计划 F2、风险表、验收矩阵、规格分歧；不能留给实现者猜“任一授权满足即可”。0062:21–25 描述的也不是逐风险档位 allowlist，而是带 Project 排除的 workspace 模式，YOLO 可满足任意风险级别。见 H2。

### 3. B1 的残余

**原则保留正确**：ADR:266–283、297–304 和计划:524–534 明确自由文本不是 grant、保留真实 agent 作者、禁止自行扩权、任意 final/decide 记录不作授权，并要求共享 guard。

“文本不是授权”不等于“收到文本后永远不能执行”：已有合法 standing delegation 时，文本可以提供任务输入，范围内可自主分派。应测试“无有效委派时文本不能创造权限”与“有有效委派时文本不能扩大范围”，而非恢复旧测试“所有自由文本都不得触发执行”。恶意文本在合法范围内影响决策是输入质量风险，本轮没有证据把它认定为权限越界。

需要封住的具体设计路径是：消息/提案 → YOLO Approval → 新增/扩展委派（H2），以及消息内容 → 指派一个已有更宽权限的执行者 → 超出本目标分派上限（H3）。它们是**待验证的绕过路径**，不是本轮已复现漏洞。取消逐次 canonical action digest 并不自动破坏 B1；Human 建立/修改委派时的确定字段与 revision 绑定、执行请求的幂等内容校验仍必须保留。

| 验收矩阵（639–643） | 已测试范围内自主分派/范围外拒绝/真实 source；缺并发撤权、派生 executor、配额、YOLO 两路径与两道关口断言 |
| 状态行（4） | owner 口径与 F5 未决状态正确；F0/F2 依赖歧义见 L1 |
| 依赖图（238–241） | F2 名称漏改，且与状态行方向不一致 |

计划:21–35 是本批仓库工作的执行记录例外，并明确不改变 WorkMesh 产品控制面，不能拿该段的总管合并授权去解释产品默认能力；本次审查的只读限制也不受它改变。

### 6. 人称与术语

| 英文概念 | 中文对应与判断 |
| --- | --- |
| Chief / designated coordinating agent | 总管 / 被任命的协调 agent，一致；不是新增 actor kind |
| Human / principal Human / Responsible Human | 人类主体 / 授权委托人 / 工作项负责人；语义有区分，F3 保留 principal 等于目标负责人 |
| Chief delegation / standing delegation | 总管委派 / 常设委派，一致；“常设”表示可重复使用至到期或撤销，不是永久有效 |
| appointment / revision / revocation | 任命 / 修订及版本号 / 撤销，主要对应一致；人的“修订操作”与请求携带的 revision 版本应保持区分 |
| Approval / delegation | 动作审批 / 有界委派，不能统一写成无区分的“授权”，见 H2 |
| Dispatch authorisation / consumable binding | 分派授权 / 可消费绑定，仍是旧概念残留，见 M2 |
| two human gates / 两个执行关口 | 英文明确 Human，中文正文列“确认方案/审核改动”；是否要求真人、如何受 0062 影响未定义，见 H2 |

未发现执行命令作者被新文字改写为 Human；恰恰两边都显式禁止这种身份伪装。“人可修订”表达的是控制方式，不授予任何任意 Human 越权修改权限。

### 7. 默认排除与两个关口

能力表仍完整列出 17 项，默认六项与单独批准十一项互斥；`merge` 的准确枚举名是 `repo:merge`，`deploy:*` 在表中具体是 `deploy:staging` 与 `deploy:production`。**直接能力的默认排除没有被此次文字修改删除**，F1 还专门测试原本有 merge 的 agent 在 Chief 会话中不带该能力。

但该表只证明 Chief 自己的直接能力边界，不能证明下游执行边界（H3）。两道关口在 ADR:295、计划:529 仍被明确保留，未被删除；只是目前没有足够契约确认在 YOLO、自主派工、plan/head 变更时如何保持有效（H2）。ADR 0020 的精确 head、独立结构化审查、检查结果与执行前复验也未被这次修改撤回；不能把“自主派工”解释成自动获得 merge/deploy 权限。

## 必须改清单

1. **H1**：写明修订/撤销的并发顺序、排队工作与运行中派生工作的失效规则，以及外部执行的可撤销边界。
2. **H2**：将“同构”改为两个不同授权层的合取关系；明确 grant 创建/扩展的 Human 命令；为两道执行关口定义 actor/source 与版本绑定。
3. **H3**：明确直接能力与可分派下游能力/资源上限，补已获宽权限目标 agent 的反向用例。
4. **M1**：补可复用委派的原子用量/预算台账及并发、重放、失败语义。
5. **M2**：清掉迁移和 Spec changes 中的可消费逐次授权，独立保留分派身份与效果去重。
6. **L1**：同步计划依赖图和状态行，区分设计冻结与实现前置；风险表和验收矩阵加入上述缺口。

## 这次修订最强的一条

**把“给任务即放权”落在结构化、有界、可撤销的委派上，同时继续排除自由文本授权。** 这正确区分了输入、任命、授权与执行者身份：人一次确定目标和边界，总管在边界内作日常调度，人以修订和停止纠偏。配合既有服务端授权检查，这比要求每项派工重新由人确认更符合协调者职责，并不天然牺牲 B1。

## 这次修订最脆的一条

**把“有一个可撤销授权引用”直接等同于“每次分派及其运行结果都可撤销”。** 常设授权会跨多次提交、多个执行者和多个异步队列；其中任何一个派生权限脱离来源委派的实时边界，“人可修订”就会只影响下一次派工而无法约束已经排出的工作。当前只写 later dispatches 与 Chief 旧会话拒绝，没有给出这条关系上的失效契约，这是比措辞“并行”更直接的安全薄弱点。

## 明确没有问题的部分

- 自主分派方向本身与 actor/Delegation 模型相容；无需退回逐次人类决定。
- 任命不授予能力、不新增第四类 actor、Responsible Human 不可被 Chief 替代，仍成立。
- B1 的自由文本不授权、真实作者不伪装、final/decide 不能充当 grant，均被正确保留。
- 五个入口共用 guard、持久 Chief 执行上下文、一般能力/scope/Stop/lease/revision/idempotency 检查，均仍明确要求；本轮没有把它们当作已实现验收。
- 默认排除的直接能力列表没有被放宽；拓宽必须是单独可审计的 Human 行为。
- 跨工作项 principal 必须等于目标 Responsible Human、任命更换原子性、租约不授权，未被此次修订削弱。
- 0062 的真实策略来源保留在计划矩阵中；政策批准不伪装成人类逐次批准这个方向正确。
- 两道执行关口没有被文字删除；需要补定义，不应声称已经确认其运行时失效。
- 历史撤回段的 per-dispatch / exception 属于必要记录；事件消费协议不属于旧的逐次授权消费。
- 未决的 F5 收件恢复选择仍明确标出，没有被这次分派修订假装解决。

**一句话总评：接受“委派内自主分派、人以修订介入”的方向，但在撤权传播、双层授权组合、下游权限和用量计数写成可测试契约，并清理旧规格出口之前，不能确认本次放宽没有引入新的授权缺口。**
