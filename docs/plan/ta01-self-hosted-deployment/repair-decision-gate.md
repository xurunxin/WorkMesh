### H1：事务内来源快照的规划或执行成本使企业 ARM 越过期限

单次组件资格请求有 45 条 SQL、身份 COMMIT 累计 7.45 秒；最慢客户端模板 2.25 秒，另一次同模板 0.56 秒。模板定位到 `appendEvent` 的通知来源快照。`agent-connections.ts` 的首次实时身份建立包含 `agent.session.created` 事件；来源快照在原事务内执行，随后才有事件和 outbox 事实。

`notificationSourceSelectionSql` 使用宽 Human Attention 投影并按来源、收件人、revision 筛选。SQL 文本宽不证明数据库实际执行了全部分支或计算了所有 JSON 列。原件缺该失败请求的逐语句规划、执行及等待关联，不能把客户端 wall 或整库最大规划时间当本次 SQL CPU。

**最小证伪条件：**在原企业升级后 commit 序号16中，若精确模板的服务端耗时很小而客户端仍长，则“该模板服务端成本主导”不成立；若模板的规划或执行持续占据失败请求，则再评估等价窄投影。一次未超时仍不能排除原故障。

候选窄投影尚未实现。若后续证据支持，须先以原生隔离 PG 对旧／新查询做集合等价及计划对照，覆盖全部八类 aggregate、五类直接来源与关联 Inbox、open／closed、受众、room visibility、来源 revision 和重复交付。并发更新下的事务快照、事件与 outbox 原子性必须保持。已有 `notification-channels.integration.test.ts` 的精确收件人快照用例只能提供回归基础，不能替代新增等价证明或 ARM 性能证据。

### H2：实时资格生成、验证与序列化成本使组合读取超时

组件资格 handler 尾段为 4.03 秒，包含生成、严格校验、序列化和公共 onSend，未拆成纯函数 CPU。源码中 `createAgentCapabilityManifest` 组装并校验 manifest，`qualifyAgentCapabilityManifest` 加入实时资格后再次校验；不能因为两次 parse 就断言其中一次无用。

`apps/mcp/src/discovery.ts` 只拦截工具／资源方法；普通 `get_work_item` 先 `prepare()` 取得实时资格，再调用工作项处理器。`initialize` 不走该资格路径。因此资格成本可以是工具读取解释的一部分，**不能解释尚未进入此路径的 initialize 139**。组件的两个关联只覆盖 API 内部，不补出原 CI 的 MCP 全链路。

**最小证伪条件：**同一失败窗口若资格已及时完成、工作项或客户端仍占据余下期限，则“资格生成单独足以解释失败”不成立。若独立测得生成是主要成本，可考虑只预生成与 actor／session／feature 无关的静态操作元数据；每请求仍组合实时状态、能力交集与 scope，并保留边界校验。须逐字响应等价、撤权即时拒绝和不同身份／feature 无串用证据，才可实施，不能缓存资格或跳过 parse 取绿。

### H3：VM 调度、存储布局、竞争负载或观测影响了响应

组件连接取得最大 24.95／4.97 ms，不支持本样本存在秒级连接取得排队。27／11 次等待采样未见 Lock，只能记录未观测到，不能排除间隙等待或原 CI 的等待。独立 API、只读 ISO、PG 参数、额外统计和缺少生产负载均与实际安装组合有差异；原生行锁对照只证明采集有效。

**最小证伪条件：**保持原镜像和运行布局，在同一失败窗口分列客户端 wall、服务端规划／执行、进程 CPU 增量及调度等待。如果已有长服务端执行而进程持续有 CPU，则不能仅归于客户端调度；如果服务端短而客户端长，则不能以 SQL 生成成本单独解释。采样开销本身须计数、限频并披露；无法可靠关联就记未知，不能靠相减补齐。

### H4：139 和总期限缺件属于尚未定位的独立失败路径

旧 API139 没有 core；MCP139 的有界公开帧只有执行位置，未定位坏值或其来源。initialize 不读资格，有限原生／TCG 小测未复现也不能排除依赖运行时、产品对象生命周期或 VM 环境。现有证据不足以选择其中一种，更不足以改 Node、QEMU 或重启策略。

个人／团队 ARM 最后分别是 restore-empty 序号23、recover-old 序号21开始，9,000 秒到期且无最终回执。动作名不提供内部阻塞点；不能套企业读取超时、宣称恢复完成，或据缺件推实际请求数。后置诊断开销不能倒因解释此前出现的139。

139 需有准确二进制、实际故障进程及最早公开帧与原请求边界的因果证据；总期限路径需先取得原动作的内部回执。两者均未满足。下面选项只针对企业 ARM 读取，不承诺解决这两类缺口。

## 待裁定的最小下一步

当前证据不足以安全选择产品修复。建议裁定是否允许**一次原企业 ARM 安装组合的定向取证**，而不是续跑组件小测或六组合矩阵。以下为待批准方案，尚未编写或执行新助手；批准前不配置 PG、不启动 VM、不 dispatch：

1. 使用 CI567 的准确企业 ARM 候选、原 guest／Node／QEMU／固件／设备和 4 vCPU／4 GiB。先核生产者12043116531及 manifest `12eb5978a939da8d643caf70bc14e8b13326cdec5f3cf82f0c3b2f0ec212fa1f`、原输入与脚本摘要；任一不可得即停，不换版本外推。镜像字节、entrypoint、真实身份、布局和业务路径不改。
2. 一台隔离 guest，总窗仍最多 9,000 秒；原安装1,800秒、健康180秒和业务30秒保持。精确承接企业原动作前缀至升级后正常 commit 序号16，只执行原请求一次。若更早失败，保存首败即停；若目标成功，也只报告本样本成功，不自动继续恢复链或另开运行。
3. 仅在目标原 commit 前准备限频的外部 PG／进程观测，原 API correlation 摘要与代理序号作边界。PG 保持连接池与内存参数，只在隔离目标上记录查询标识、backend PID、模板摘要、规划／执行数值和等待类别；进程只投影 CPU／调度数值。采样至多每秒一次、最多90秒，不能延长30秒客户端期限。不得收集 SQL 参数、凭据、正文或原始私有日志入库。需要开启 PG 规划／语句耗时观测是本选项新增的诊断设置，不能冒作原环境无开销；若现有镜像不具备所需能力，不安装扩展或自动改配置，直接记缺口并停。
4. 先保存已有安全回执和首次失败，再收尾；无统一关联不拼造阶段。原公开候选与共享镜像复用，可写 guest／数据库／卷独有登记。仅按准确归属收尾，不触碰旧树、共享数据、未知卷和受拒目标。超窗、缺件、采样失败或取回失败均记 incomplete，不能自动补第二台或续用1,800秒例外。
5. 成功取证的判据是能对同一原请求分辨连接取得、服务端 SQL 成本与响应／客户端边界，并给出可核关联和采样开销；它不是产品 PASS。不能单凭本次未复现来关闭旧失败。只有某个解释得到直接支持，才提交保持保证的最小产品补丁及旧／新定向对照；否则停回关口，不追加运行。

如果不批准该新 VM 取证，就保持关口，保留现有证据，不实施猜测性优化。可在原范围继续静态审阅，但不把它说成原 CI 根因证明。本方案不申请 runtime、资源、权限、设备、产品期限或支持矩阵变化；也不自动批准下一轮139捕获或个人／团队恢复诊断。
